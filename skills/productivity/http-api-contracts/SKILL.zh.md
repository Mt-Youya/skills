# HTTP API 契约与实现规范化

[英文版本](SKILL.md)。英文为默认入口；中文版描述相同流程，不作为独立 skill。Skill 编写语言不覆盖用户或工作区的回复语言要求。

把“符合规范”落实为三层证据：HTTP 行为正确、机器可读契约有效、真实请求和响应与契约一致。文档通过元 Schema 校验不代表运行时合规；测试全绿也不代表已覆盖所有接口。

## 按需加载

- 每次接口任务先读 [规范核对清单](references/standards-checklist.md)，仅应用相关项目。
- 涉及代理、网关、SSE 或流式计费时再读 [转发与流式边界](references/proxy-streaming.md)。
- 涉及 Rust/axum、Cloudflare Fetch 或全量规范化时读 [此次实践与通用陷阱](references/implementation-lessons.md)。
- 使用新的规范版本、遇到争议或准备引用条款时读 [权威来源与版本策略](references/sources.md)，定位相关原文，不把记忆或搜索摘要当作标准。

## 1. 确定范围，而不是猜测架构

1. 阅读仓库规则和当前差异，保留用户修改；查看真实路由、部署入口、代理层和已有测试。
2. 从用户意图区分：只审查、修具体问题、新增接口、完整契约化。单点任务只改影响范围，不为一个 bug 引入全站契约注册框架。
3. 若范围不明且不同解释会引起实质不同或大规模改动，先展示已确认的问题，再询问范围与不兼容边界。用户已明确回答时不重复询问。
4. 默认保留路径、字段、认证机制和业务语义。对必需的不兼容改动说明原因、影响客户端及迁移方式；先取得范围授权，不把“规范”当成无限重构授权。
5. 明确角色：源站、HTTP 代理、应用协议网关、客户端。不同角色的认证挑战、Via、头部转发义务不同。
6. 明确验收：复现输入、预期状态/响应头/正文、契约版本、客户端兼容、业务副作用与可运行的门禁。

先给简短计划与假设，随即执行；不先说“都符合标准”再寻找证据。

## 2. 建立事实清单和差异证据

按实际注册梳理受影响操作：method/path、handler、path/query 参数、请求媒体类型与 DTO、成功/错误状态、响应头和正文、认证/授权/CSRF、是否流式、调用客户端。

检查最终对外服务，而非仅检查 handler：提取器、路由器、认证、代理、响应封装、服务器编码器都可能新增响应分支或重写头部。

给每个发现标记类别：

- **规范硬性要求**：附标准版本、条款、适用角色及真实代码/输入证据。
- **语义或契约不一致**：说明什么输入产生何种差异；不要伪称为 RFC 的 MUST。
- **项目政策或建议**：例如统一错误封装、Location 策略、超时预算、JSON-only 成功响应。
- **待验证风险**：框架行为、运行时能力或外部依赖尚无证据，先复现再定性。

不要将动作型 POST、没有通用 data envelope、未使用 Problem Details、所有校验不返回 422、201 没有 Location、429 没有 Retry-After 自动认定为违反这些规范。

## 3. 让契约有唯一可信来源

优先沿用项目的 spec-first 或 code-first 机制。不存在机制时选择最小、可维护方案；使用标准生成器和校验器，不写一个阉割版 JSON Schema 引擎。

- 固定 OpenAPI 版本和 Schema dialect。此次基线为 OAS 3.2.1、Draft 2020-12；升级需核对生成器、校验器及客户端支持，不能只改版本字符串。
- 请求与响应分开建模：反序列化的可缺省字段不等于序列化时可以省略；必填、可空、未知字段及默认值必须对应实现。
- 响应来自 SQL/手工 JSON 时核对实际投影与序列化；类型名存在不保证返回字段齐全。敏感内部模型不要直接导出。
- `paths`、参数、媒体类型、security 的 AND/OR、响应状态、关键响应头都应完整；自动 HEAD 与 CSV/SSE 不得伪装成普通 JSON。
- 承认真实开放边界：上游协议透传可以使用开放 Schema，并说明本地与上游分别校验哪些字段。不要虚构完整 provider DTO，也不要用空 Schema 掩盖本地固定响应缺失。
- 对 `$ref`、`$id`、`$defs` 与 components 处理保持引用基准一致。配置实际支持的 dialect；远程引用按明确网络与信任策略处理。
- 校验 OpenAPI 文档结构、每个 Schema 的元 Schema、实际数据实例。三项结果分别报告。
- 同步客户端和调用方测试。生产响应校验不是默认要求；可在测试/开发环境验证，避免生产缓冲大响应或 SSE。

若实现暂时无法完整描述，明确缺口和条件，不宣称“全部完成”。

## 4. 修协议边界，不绕过业务

- 401 需要适用于目标资源的 `WWW-Authenticate`；scheme 大小写不敏感、凭证值不随意改写。Cookie 认证也不豁免，但不能虚假声明支持 Basic/Bearer。
- 405 保留真实 `Allow`；未知 API 路径与浏览器导航分开处理。是否跳转属于项目契约，不能让 JSON 客户端意外收到前端页面。
- HEAD 不带正文；204 不带正文或 Content-Length（0 也不允许）。304 不带正文，Content-Length 只可表示对应 200 的表示长度。
- 框架可能在 handler 之后设置长度。必要时在已完成路由处理的服务外层规范化，并用原始 HTTP 验证，而不是盲目叠中间件。
- 区分语法、大小、媒体类型、结构及业务校验；状态码与错误封装按实际语义和契约选择，不机械把全部错误改为 400 或 422。
- 认证基础设施故障不证明凭据失效，不把数据库异常变成 401。上游故障区分 502/504 与本地 500；超大响应等政策另行明确。
- 错误包装保留挑战、Allow、Cookie、请求 ID；不泄漏数据库错误、密钥或带凭据的 URL。
- 保持原始请求字节直到消费需要，避免额外序列化改变计费、签名、幂等摘要或验证依据。
- 不改变预占/释放/核对/结算及 Webhook 幂等规则来迁就 HTTP 测试；把业务副作用列为回归断言。

## 5. 验证闭环

先写最小复现或回归，再实施，最后经过最终服务验证。

1. **协议回归**：相关状态码、401 多挑战、405 方法集合、HEAD、204/304、媒体类型、大小限制、路径/query 提取和响应字节。
2. **契约回归**：元 Schema、引用、真实 DTO 序列化/反序列化、合法/非法/缺失/null/未知字段/边界值。
3. **真实 HTTP**：运行实际路由和代理，校验成功及错误响应。Schema 生成的样例只能补充，不能替代真实数据；数组至少测试一个非空实例。
4. **业务回归**：认证/角色/CSRF、数据库投影、重复写入、并发、账务或签名证据。数据库使用框架隔离库，确认与源数据库不同，不硬编码本机用户名或服务地址。
5. **交付门禁**：项目测试、类型检查、构建、适用的配置 dry-run；修改文件诊断、格式、行数约定和 diff 检查。
6. **独立复查**：重点查运行时与声明、流式背压、多值头和实际成功响应。并行任务分配互不重叠的文件，整合后重跑；不要覆盖别人的测试。

联网测试与离线门禁分开。缺数据库、外部服务或工具时说明阻塞，不跳过失败后宣称通过。不伪造执行次数、性能指标或验证证据。

## 6. 交付报告

遵守用户和工作区的回复语言要求；skill 默认用英文编写不改变这些要求。简洁说明：

- 实际改动与接口/目录范围。
- 采用的规范版本、规范问题与项目政策的区别。
- 不兼容变化及客户端调整。
- 已执行的验证、通过数量、实际覆盖分子/分母。
- 忽略的联网测试、未验证的运行时限制和剩余缺口。

没有得到请求时，不提交、部署、重写 Git 历史、新增项目 README 或设计文档。skill 的自动触发由宿主加载目录和 description 决定，不声称其是不可绕过的门禁。

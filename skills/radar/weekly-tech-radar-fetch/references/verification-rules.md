# 核实规则

> 本文件包含 URL验证、交叉核实、聚合文章防范的完整规则。
> SKILL.md 在执行第六步时读取本文件。

## URL验证（第五步，强制，不可省略）

**历史教训：** Agent 曾在采集时根据文章标题自行推断URL slug（如把 `an-alien-mind` 写成 `alien-mind`），导致27条链接中23条是404。RSS feed 的 `<link>` 字段就是文章真实URL，必须直接使用它，绝不能从标题推断。

**验证规则：**
1. **RSS/feed 条目的 URL**：直接使用 RSS `<link>` 字段的值，**不要从标题推断 URL slug**
2. **web_search 找到的条目**：直接使用搜索结果里返回的 URL
3. **任何候选的 link 字段不得为空、不得是首页、不得是编造的**
4. 如果 link 字段看起来像是首页（如 `https://openai.com/news/`、`https://github.blog/`）而非具体文章，**丢弃这条候选**——没有精确URL的条目没有发布价值
5. 如果 link 字段的 URL 与标题明显不匹配（如标题提到 Cybercab 但 URL 里包含 nvidia），**丢弃这条候选**

## 交叉核实规则（第六步）

### 规则0：官方一手源与高可信新闻免双信源验证（Layer 1 和 Layer 2 适用）

**判断原则（不是封闭列表）：** 以下两类信源的内容不需要找第二个独立信源印证——它们本身就是最高可信度的信息来源：

**Layer 1 官方一手源**：公司/机构在自己官网发布的关于自己的内容。官方发布本身就是可信的第一手事实。

**Layer 2 高可信新闻**：**任何具有国家级公信力的政府机构、官方通讯社、权威媒体的原创报道。** 包括但不限于：
- 国际：Reuters、AP、AFP、Bloomberg、Financial Times、Wall Street Journal 等
- 中国：新华社、人民日报、央视新闻(CCTV)、中国政府网(gov.cn)、国务院各部委官网、中国新闻网、财新网 等
- 其他国家：各国家级通讯社、政府新闻办公室、国家级广播电视机构 等

> **关键：这不是一个穷举列表。** Agent 应根据来源的公信力自行判断——如果一条报道来自某个国家的政府官方渠道或具有严格编辑审核流程的权威新闻机构，它就属于高可信新闻，免双信源验证。判断标准是"这个来源是否有国家级公信力"，而不是"这个来源是否在列表里"。

免双信源验证仍需满足：
1. **发布日期在48小时窗口内**
2. **内容是事实报道不是纯观点/预测/评论**：区分"Reuters报道OpenAI发布GPT-5"（事实报道，收录）和"FT评论认为AI泡沫即将破裂"（观点/评论，不收录）
3. **聚合文章陷阱仍需溯源**：如果是"本月总结/季度回顾/周报盘点"这类聚合内容，仍需拆开看每条事件的真实发布日期

`verification_notes` 字段写法：
```
{来源名称} {官方博客/新闻室/原创报道} {发布日期} 发布，内容为{当事方关于自身的事实公告/权威媒体原创事实报道}，免双信源验证
```

### 规则1：非官方信源需要第二个独立信源印证（Layer 3/4 适用）

对于来自 Layer 3（科技媒体）、Layer 4（中文补充检索）的候选：
- 用 `web_search` 搜索这条资讯的关键词，找到至少一个独立于原信源的第二信源
- 两个信源都指向同一个事件，且发布日期一致，才算通过核实
- 如果只有一个信源，或者找不到第二个独立信源，**直接舍弃这条候选**

`verification_notes` 字段写法：
```
第一信源：{来源名称} + {链接}
第二信源：{独立核实信源名称} + {链接}
核实结论：一句话说明
```

### 规则2：聚合文章陷阱——必须溯源（所有层级适用）

如果候选条目的标题或来源包含以下关键词：`周报`、`月报`、`盘点`、`汇总`、`roundup`、`recap`、`digest`、`weekly`（作为标题词而非信源名）

- 这类文章是聚合转述，其发布时间不代表里面每条事件的真实发生日期
- 必须对文章里提到的每个具体事件，单独搜索其原始发布日期
- 如果原始事件的发布日期不在目标窗口内，**舍弃这条候选**

> **典型反面案例**：某"AI周报"文章发布于 2026-08-07，文中提到"Wan 2.6 发布"——但 Wan 2.6 实际发布于 2025年12月。如果不溯源，就会把一条 8 个月前的旧闻误收录为"本周新闻"。

### 规则3：核实不了就舍弃（所有层级适用）

- 如果无法找到可靠的第二信源（非官方信源），或者无法确认真实发布日期，**直接舍弃**
- 宁可这周条目少，也不收录无法核实的内容

### 如何判断一条内容是否属于"官方一手源"

判断原则：**这条内容是不是当事方（公司/机构/项目团队）自己在自己域名下发布的关于自己的内容？**

- ✅ `openai.com/blog/xxx` → OpenAI 在自己官网发布的关于 OpenAI 自己的内容 → 官方一手源
- ✅ `anthropic.com/news/xxx` → Anthropic 在自己官网发布的关于 Anthropic 自己的内容 → 官方一手源
- ✅ `developer.apple.com/news/xxx` → Apple 在自己开发者站发布的关于 Apple 自己的内容 → 官方一手源
- ❌ `techcrunch.com/2026/08/xx/openai-xxx` → TechCrunch 转述 OpenAI 的新闻 → 不是官方一手源，需要双信源验证
- ❌ `36kr.com/p/xxx` → 36氪转述某公司的新闻 → 不是官方一手源

如果不确定一条内容是否属于官方一手源，按"不确定就当不是"处理——走双信源验证，更安全。

## Layer 5 核实要求（GitHub Trending）

1. GitHub Trending 榜单数据本身是 GitHub 官方的事实——哪个项目上榜、新增多少 star，是平台直接计算的客观数据，跟 Layer 1 官方一手源同一性质
2. **不需要找第二信源验证"这个项目确实上榜了"**
3. **不需要找到"为什么突然火"的具体触发事件才收录**——星标增长本身就是有价值的开源热度信号
4. 仍需满足：发布日期（抓取日期）在48小时窗口内、内容是事实不是观点
5. 候选标题和摘要应描述项目本身的关键信息（项目名、简介、star增长数、主要语言）
